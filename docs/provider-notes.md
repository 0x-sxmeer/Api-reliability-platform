# Provider notes (Phase 2, extended in Phase 3)

Every claim below is tagged VERIFIED (confirmed against an official,
first-party document, fetched or searched this phase) or UNVERIFIED
(secondary source, community report, or inference). Adapters must not
encode an UNVERIFIED claim as a hard-coded, silently-trusted fact —
where one shows up in code, it's called out in a comment pointing back
here.

Anthropic's entries are carried over from the existing (Phase-2-in-progress)
adapter, re-checked against the same class of sources it cites. I did not
re-fetch Anthropic's docs myself this session — flagged as such below,
distinct from OpenAI/Gemini which I fetched/searched fresh.

| 503 `service_unavailable_error`/`server_is_overloaded`: "the requested model does not have enough capacity to process your request at the moment" — analogous to Anthropic's 529, i.e. provider capacity, not caller quota | VERIFIED | official error-codes guide |
| `APIConnectionError`: request never reached OpenAI's servers (network/proxy/TLS/firewall) — a transport-level failure distinct from any HTTP status | VERIFIED | official error-codes guide |
| Usage tiers (Free/1-5) gate rate limits and scale with cumulative spend; e.g. Tier 1 at $5 paid, Tier 5 at $1,000 + 30 days | VERIFIED (current official table) | official rate-limits page |
| Some model families share a rate-limit pool across models ("shared limit" list) | VERIFIED | official rate-limits page |
| Vector store ingestion has its own separate per-vector-store-ID rate limit | VERIFIED | official rate-limits page |

**Limiting unit, stated plainly:** OpenAI is **dual-scoped** — organization-level limits AND project-level limits can both apply to the same call, with project-level headers appearing "when a project-scoped limit applies." This is different from Anthropic (single scope: organization) and forced `LimitingUnit` to be treated as "the primary scope this adapter reports," with the project-token headers originally preserved in `raw_headers` only. **Phase 3 promoted them** to `RateLimitSnapshot.additional_scopes`, because the Quota Engine needs the *binding* scope per response (a fixed `get_limiting_unit()` cannot say which of the two is tighter) — see Interface Change Log #8.

**Not verified / explicitly out of scope this phase:** exact current numeric limits per tier per model (these live in a personal dashboard, not a fetchable public doc, and change too often to hard-code); the newer `insufficient_quota` vs `organization_usage_limit_exceeded` vs a configured spend-limit error are three distinct things by the docs above, but I did not find a documented way to distinguish a *configured project spend limit* 429 from a *configured org spend limit* 429 by `code` alone — both may simply be `insufficient_quota`. Adapter comments flag this as UNVERIFIED.

## Google Gemini

Gemini has **two live API surfaces** as of this research, and they have genuinely different error shapes. This matters enough to state up front:

- **`generateContent`** (`POST /v1beta/models/{model}:generateContent`) — the original, stateless surface. Google's own docs call it legacy but state it "remains fully supported," and it's what the SDKs, third-party gateways, and nearly all existing integrations use today (a July 2026 third-party gateway compatibility check found the newer Interactions API returning 404 through that gateway, while `generateContent` worked normally).
- **Interactions API** (`POST /v1beta2/interactions`) — GA since June 2026, Google's recommended surface for *new* projects, stateful/step-based responses. Its error page (verified, official, last updated 2026-09-20) documents a **cleaner** error model: distinct machine-readable codes `rate_limit_exceeded` (429, per-minute/token) vs `quota_exceeded` (429, daily quota) vs `too_many_requests` (429, generic) as three separate `code` values in one flat `error.code` field.

**Decision, flagged for review:** the adapter targets **`generateContent`**, because it's what's actually integrated against today and what nearly every real deployment will call. The Interactions API's cleaner error codes are documented below for when a future phase adds it as a second Gemini adapter variant (`gemini-interactions`?) — not folded into this one, since mixing two different response shapes into one `classify_error` invites exactly the kind of silent misclassification this project exists to prevent.

**`SignalQuality` decision for Gemini, stated plainly:** `generateContent` gives **no rate-limit headers on any response**, success or failure — so every `RateLimitSnapshot` for Gemini has `signal_quality = SignalQuality.NONE` (not `PARTIAL`) on success responses. On a 429, there **may** be a `QuotaFailure`/`RetryInfo` body to parse — this is surfaced through `classify_error`'s `ClassifiedError`, not through `parse_rate_limit_headers`, since it's error-body detail rather than a per-response quota snapshot, and it is explicitly `is_definitively_classified=False`-eligible per the UNVERIFIED note above when the `quotaId` string match is the only evidence.

## Cross-provider summary (what actually generalizes)

| Question | Anthropic | OpenAI | Gemini (`generateContent`) |
|---|---|---|---|
| Rate-limit headers on every response? | Yes | Yes | **No — none, ever, documented** |
| Limiting unit | Organization — **and optionally a lower workspace scope that the headers can't distinguish** (Phase 3 finding) | **Both** org and project simultaneously (project headers: tokens only) | Project (single scope, explicitly NOT per-key) |
| Counters further partitioned by (Phase 3) | Model class (token bucket; `reset` = fully replenished) | Model, with org-defined shared pools | Model (VERIFIED limits vary by model; per-model *counters* VERIFIED-by-example) |
| Can the gateway learn the numeric limit from the provider? (Phase 3) | Yes, `*-limit` headers | Yes, `*-limit` headers (incl. `limit-project-tokens`) | **No** — AI Studio only; must be operator-configured |
| Is "overloaded" distinguishable from "rate limited" by status code alone? | Yes (529 vs 429) | Yes (503 vs 429) — **but a 2026 migration moved some overload-adjacent cases from 503 to 429 with `code: slow_down`, so `code` must be checked even on 429** | **No** — both are 429 `RESOURCE_EXHAUSTED`; only a body-level (undocumented-as-contract) `quotaId`/`details` heuristic can try to separate them |
| Is "quota exhausted, retry is futile" distinguishable from "rate limited, retry works" by status code alone? | No (both 429; needs `error_code`/absence of `retry-after`) | Yes, by `code` field (`rate_limit_exceeded` vs `insufficient_quota`) at the JSON level, same 429 status | No (both `RESOURCE_EXHAUSTED`; only the heuristic `quotaId` string) |
| Any provider where a documented, official, stable machine-readable field cleanly separates every category this project cares about? | Partially (needs body inspection past status code) | **Closest to clean** — distinct `code` values, though still same HTTP status | **Least clean** — relies on unverified-as-contract heuristics |

This table is itself a finding: **the original interface's `SignalQuality` enum, forced by Gemini's missing headers, turns out to also need to express "the error body has parseable detail, or doesn't"** as a related-but-different axis from header quality. See Interface Change Log for how this phase resolved it (or didn't, if deferred).
